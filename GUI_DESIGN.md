# GUI Design Guide

## Purpose

This document defines the preferred design approach for the desktop GUI. It is
intended to help contributors and agents create a consistent, intuitive,
scalable, and secure user experience.

The GUI should guide users through operational workflows without requiring them
to understand the underlying API calls or internal code structure. It should
expose enough context to make the current state, available actions, progress,
and failures immediately understandable.

## Core design principles

### Design around user workflows

Organize the interface around the task the user is trying to accomplish, not
around individual API endpoints.

A workflow may combine:

- credential discovery;
- certificate trust establishment;
- device inspection;
- configuration changes;
- account or resource selection;
- remote service operations;
- generated-code handling; and
- final device-side completion.

The GUI should present these as a coherent sequence while allowing users to
enter an existing workflow midway when valid inputs or artifacts already exist.

### Use shared application services

The CLI and GUI must call the same application services and validation
boundaries.

Do not duplicate business logic, endpoint selection, credential policy,
compatibility handling, or licensing decisions in GUI event handlers. GUI code
should primarily:

- collect and validate user input;
- invoke shared services;
- display progress and results;
- manage presentation state; and
- request explicit confirmation for consequential operations.

### Prefer registry-driven presentation where appropriate

Common workflow actions should be described using presentation-neutral metadata
when this improves consistency and maintainability.

Suitable metadata includes:

- operation identifier;
- user-facing title;
- handler;
- prerequisites;
- ordering; and
- capability grouping.

Do not attempt to generate the entire GUI directly from an OpenAPI schema. API
specifications do not capture operator workflow, security policy, recovery
paths, or meaningful interaction design.

Use metadata-driven rendering where it creates a clear reusable abstraction.
Retain purpose-built UI logic for workflows that require specialized behavior.

## Workflow presentation

### Show staged progress

Actions should visually communicate whether they are currently available.

Preferred workflow button states are:

- Available: light green background with black text and a visible border.
- Unavailable: white background with very light gray text and border.
- Running: disabled while the associated task is active, with progress shown
  separately.
- Failed: re-enabled when retrying is safe, with a durable error message.
- Completed: update the workflow state so the next valid actions become
  apparent.

Buttons should become available as their prerequisites are satisfied. Do not
rely only on instructional text to tell the user what can be done next.

### Allow safe mid-workflow entry

Users may already possess an artifact generated outside the application, such
as an authorization or return code.

Where safe and meaningful, the GUI should allow users to paste that artifact and
continue from the appropriate stage. Labels and actions must describe the
artifact's current purpose rather than assuming it was generated by the
application.

For example:

- Use `Configure PLR` instead of `Generate Request Code` when the operation
  encompasses more than code generation.
- Use `Authorization or Return code (generated or pasted)` for a shared handoff
  field.
- Change the associated action between `Install Authorization Code` and
  `Submit Return Code` based on the active workflow.

### Make consequential transitions explicit

Mutating operations should require clear confirmation unless the application is
operating in an explicitly defined unattended mode.

Confirmation messages should identify:

- the target device or resource;
- the operation being performed;
- the selected account or scope when relevant; and
- any important consequences or required follow-up.

Do not use an immediate confirmation dialog when the user must first preserve a
one-time artifact. Keep the artifact visible and require a separate, clearly
labeled action to continue.

## Background work and progress

### Keep the GUI responsive

All network calls and other potentially slow operations must run outside the GUI
thread.

Completion and failure callbacks must be marshalled back to the GUI thread
before updating widgets. Controls that could start duplicate or conflicting
work should be disabled while the operation is active.

### Provide universal activity feedback

Every user-visible task that can take noticeable time should display activity
feedback. This includes:

- certificate bootstrap;
- device inspection;
- request-code configuration;
- Smart Account discovery;
- Virtual Account discovery;
- license availability checks;
- reservations;
- authorization-code installation;
- return-code generation;
- Cisco return submission; and
- final device unregistration.

The feedback should include:

- a clear description of the active operation;
- visible animation or pulsing that proves the application is responsive;
- elapsed time; and
- an expected timeout window when one is genuinely defined.

Do not present a fabricated percentage for work whose completion cannot be
measured. Use an indeterminate progress indicator instead.

A timeout describes when an operation should be considered unsuccessful; it
does not necessarily predict when the operation will complete. The UI should
make that distinction clear.

### Preserve outcomes

Success and failure messages should remain visible after an operation completes.
Users may look away during a slow task and should still be able to understand
what happened when they return.

Errors should explain:

- which operation failed;
- what is known about the failure;
- whether retrying is safe; and
- what the user can do next.

Do not reduce distinct failures to a generic message when the application can
distinguish authentication failure, missing credentials, certificate validation
failure, connection refusal, timeout, invalid input, or an unexpected server
response.

## Credential design

### Treat stored credentials as defaults

Values explicitly entered into the GUI override stored keychain values for the
current operation.

This applies independently to:

- host;
- port;
- username; and
- password.

Clearing an explicitly entered value must deactivate that override and restore
the applicable keychain fallback.

A stored password may only be used when the effective host, port, and username
match the identity associated with that password.

### Do not assume a username

Do not prepopulate a generic username such as `admin`. Different devices may use
different credentials, and an assumed username can silently select the wrong
keychain identity.

### Communicate credential state visually

Required credential fields should show one of three states:

- Missing: standard error red when neither the field nor the applicable keychain
  record supplies a value.
- Keychain: normal valid styling with `Using Keychain` shown when the stored
  value is intentionally concealed.
- Provided: normal valid styling when the user explicitly enters a value.

Typing a host that has matching stored credentials must not make the password
appear missing.

Never display a stored password in a text field.

### Scale host selection without enumeration

The Host field must remain a plain text field, not a combo box.

Behavior should be:

- If exactly one FDM host record exists, prepopulate that host.
- If multiple host records exist, leave the field blank.
- Treat the entered host as the selector.
- Perform a direct, exact keychain lookup for the typed host.
- Debounce lookup while the user is typing.
- Do not fetch, enumerate, or render the full stored host collection.

This design must remain efficient even if thousands of device records are
stored.

### Expose credential management

The GUI should provide credential-management functions for supported credential
groups, including Cisco API and FDM credentials.

Users should be able to:

- inspect whether credentials are available without displaying them;
- store a new device-scoped credential;
- replace a specified credential;
- delete stored credentials; and
- immediately refresh workflow credential state after a change.

Credential-management results must not reveal secrets.

## Selection controls

Choose selection controls based on the expected size and retrieval cost of the
data.

For small, already-loaded collections, a normal list or selection dialog is
acceptable.

For potentially large remote collections:

- do not render thousands of entries in a basic combo box;
- provide searchable filtering;
- progressively narrow displayed matches;
- avoid blocking the GUI while retrieving data; and
- avoid fetching an entire collection when the API supports direct lookup or
  server-side search.

When a selection is naturally identified by exact user input—such as an FDM
host stored in the keychain—prefer a text selector with direct lookup.

## Generated codes and sensitive artifacts

Authorization and return codes are operationally sensitive even when they are
not treated exactly like passwords.

The GUI should:

- keep generated codes visible long enough to preserve them;
- provide small, familiar clipboard and save buttons;
- support clipboard and file operations on macOS, Linux, and Windows;
- save files atomically;
- use restrictive file permissions where supported;
- avoid including codes in status or error messages; and
- clearly warn when a code may not be available again.

Icon buttons should have tooltips and accessible names so their purpose does not
depend solely on recognizing an icon.

## Certificate trust bootstrap

Certificate bootstrap should be discoverable from the workflow and should also
be offered as a recovery path when an operation detects missing trust.

The flow should:

1. Fetch only the certificate currently presented by the specified host and
   port.
2. Display its fingerprint.
3. Ask the user to verify the fingerprint through a trusted channel.
4. Persist trust only after explicit confirmation.
5. Clearly report both acceptance and rejection outcomes.
6. Continue or retry the original operation only when doing so is safe.

Unverified TLS must remain limited to the certificate-fetch portion of this
explicit trust-establishment workflow.

The GUI must not close or crash when the user accepts or rejects the
certificate.

## Layout and visual clarity

Use visual design to communicate state and focus, not merely decoration.

Preferred characteristics include:

- readable dark text on light input backgrounds;
- consistent spacing and alignment;
- concise field labels;
- clear grouping of credentials, certificate status, workflow actions, handoff
  artifacts, progress, and results;
- small secondary controls for copy and save actions;
- durable status text near the relevant workflow; and
- restrained use of modal dialogs.

Do not use placeholder text as the only label for an important field.

Colors should reinforce state, but state must also be understandable through
text, control availability, labels, or tooltips. Do not rely on color alone.

## Cross-platform behavior

GUI behavior must work consistently on macOS, Linux, and Windows.

Prefer Qt and Python standard-library facilities over platform-specific commands
for:

- clipboard access;
- file-selection dialogs;
- icons or code-drawn assets;
- credential UI behavior; and
- application lifecycle handling.

Platform-specific security behavior may be used behind a shared interface when
required, such as native credential-store integration.

## Validation and error recovery

Validate external input at its owning boundary before launching background
work.

The GUI should prevent an operation from starting when required fields are
missing or malformed. Validation failures should:

- highlight the relevant field;
- provide a bounded and actionable explanation;
- avoid clearing unrelated input; and
- return to the normal field state once corrected.

Server responses remain untrusted. Unexpected response types or missing fields
should produce a clear error rather than causing a GUI exception or crash.

Do not automatically retry mutating operations. Retry behavior must respect the
shared service's idempotency and security policy.

## Testing expectations

Every observable GUI behavior change should include focused mocked tests.

Tests should cover, as applicable:

- initial field state;
- keychain fallback;
- explicit override behavior;
- clearing an override;
- single-host prepopulation;
- multiple-host non-enumeration;
- exact typed-host credential lookup;
- button availability as workflow state changes;
- progress start, completion, timeout, and failure;
- GUI-thread callback delivery;
- certificate-confirmation acceptance and rejection;
- code copy and atomic save behavior;
- dynamic action labels;
- bounded error handling; and
- module launch and smoke behavior.

Tests must not require real credentials, display real secrets, or perform
mutating live operations.

The GUI should provide a noninteractive offscreen smoke mode that verifies the
application can initialize without prompting, accessing credentials, or
contacting the network.

## Definition of done

A GUI feature is complete when:

- it uses the shared application service rather than duplicating business logic
  where possible;
- its inputs and server responses are validated;
- slow work runs outside the GUI thread;
- progress and final outcomes are visible;
- enabled and disabled actions accurately reflect workflow state;
- keychain fallback and explicit overrides behave correctly;
- sensitive data is not exposed through status or logs;
- behavior is cross-platform where applicable;
- focused tests cover the observable behavior;
- user-facing documentation is updated; and
- the complete test suite passes.
